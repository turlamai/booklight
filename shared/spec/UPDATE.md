# Booklight Update Contract

> Online updates are the release vehicle: every platform must be able to
> check, download, verify and install a new version without the user
> hunting for download pages. The **behavior** (triggers, UX, strings,
> failure handling) is identical on all platforms; the **transport and
> install mechanism** is native to each platform, like every other part
> of the Booklight architecture. (Family contract, shared with taskly's
> `shared/spec/UPDATE.md`.)

## Behavior contract (all platforms)

- **Triggers**: one silent check shortly after launch, throttled to at
  most once per 24 h (`auto-check-interval-seconds` in
  `app/backend.rkt`; the timestamp persists as `lastUpdateCheckAt`,
  unix epoch seconds, in `updater.json` inside the config dir), plus a
  manual `检查更新… / Check for Updates…` menu item (family menu
  convention: App menu below About on macOS, Help menu on
  Windows/Linux) that bypasses the throttle (`check-updates force`).
- **Silent mode**: network failure / rate limit / throttle → silently
  ignore (never nag). Manual mode reports every outcome.
- **Newer version found** (semver compare, downgrades ignored) →
  consent dialog with the new version:
  `立即安装 / Install Now` (download + install) or cancel. Up to date →
  `当前已是最新版本 / up to date` status.
- **Download**: performed by the backend over the `check-updates` /
  `start-download` / `update-state` RPCs (rivet/distribution family
  pattern — Ed25519 manifest verify and sha256 artifact verify live in
  the backend; hosts never implement crypto). Hosts poll `update-state`
  (`phase`: idle | checking | downloading | downloaded | installing |
  error) and render progress. `start-download` is a start/cancel toggle
  while a transfer is active: a second call interrupts the worker,
  removes partial data and returns to `idle` with the candidate kept
  for retry.
- **Transfer is bounded**: 800 MiB artifact cap, a stalled transfer
  surfaces a retryable error after 120 s without progress and 30 min
  absolute (`download-stall-limit-seconds` /
  `download-total-limit-seconds` in `app/updater.rkt`); the progress UI
  offers cancel. Install failure → non-crashing error with the platform
  message; the running version keeps working.
- **Release gate**: the release workflow refuses to publish without the
  signed manifest (hard failure since the taskly-parity hardening — a
  release without a working update feed is a bug, not a warning).
- i18n keys are shared (`shared/i18n/{zh,en}.json`, `ui.update.*` and
  `update.*` families); platform copies are generated by the
  `scripts/gen-*-strings.mjs` trio.

## Platform mechanisms

| Platform | Feed entry | Install | Integrity | Failure handling |
|---|---|---|---|---|
| macOS arm64 / x64 | signed `macos`/`<arch>` zip (the DMG is the human installer, never a feed artifact) | zip → sha256 → unzip → atomic bundle swap in place, `.old` copy kept until relaunch, then relaunch the new bundle (`UpdaterInstaller`, `UpdateView.swift`) | Ed25519 wrapper signature + artifact sha256, both backend-side | swap failure or relaunch failure keeps the old bundle alive and reports; stale `.old` backups cleaned at next launch |
| Windows x64 | signed `windows`/`x64` portable zip (the MSI stays on the release for humans) | portable zip → detached `update-install.cmd` handoff: wait for app exit → extract to a fresh dir (the rivet zip's top-level layout is preserved) → swap the install directory in place → relaunch; `update-failed.txt` / success markers report the outcome on next launch (`MainWindow.Update.cpp`) | Ed25519 wrapper signature + artifact sha256 | MSI-installed copies (`IsMsiInstall()`) never self-swap — the updater points at the releases page for the new MSI (`update.msi-installed`); a failed handoff leaves the old install untouched and the marker explains it on next launch |
| Linux x64 / arm64 | signed tar.gz per arch (+ signed AppImage sidecar where applicable) | three install shapes, detected at runtime (`install_shape()` in `linux/src/host.cpp`): **AppImage** — the backend stages the new image beside the running one (verified against the signed AppImage checksum sidecar) and swaps atomically, host re-execs on consent; **deb/rpm** (exe under `/opt` or `/usr`) — no self-swap of a system-managed prefix, dialog points at the package manager; **tarball** — download kept, extraction hint | Ed25519 wrapper signature + artifact sha256 (+ signed AppImage sidecar checksum) | same non-crashing rule; a failed install never touches the running app |

## The feed URL and the two manifest names

`manifest-url()` serves `<base>/update-manifest.json` — the
family-canonical name. `scripts/make-update-manifest.sh` publishes the
same signed bytes under both `update-manifest.json` (the name this
build's updater pulls) and `update-stable.json` (the name pre-switch
installs pull). The alias retires once those installs are gone from the
field (family transition policy); until then both names are contract.

## Signed manifest files

Generated by `scripts/make-update-manifest.sh` from the release
artifacts and uploaded as release assets. Family signed-wrapper format
(`rivet/distribution`): the inner manifest travels base64-encoded inside
a JSON envelope, so the Ed25519 signature covers the exact bytes every
client verifies.

```json
{
  "schema": 1,
  "payload": "<base64 of the inner manifest JSON>",
  "signature": { "algorithm": "ed25519", "key_id": "booklight-2026-10",
                 "value": "<base64, 64 bytes>" }
}
```

Inner manifest (decoded `payload`) — rivet's manifest schema:
`application_id` `site.jrtx.booklight`, semver `version`, `channel`
`stable`, `published_at`, and one `artifacts` entry per supported
platform/architecture (macos arm64 + x64, windows x64, linux x64 +
arm64) with `url`, `sha256`, `size`, `installer` and no `component`
(single app). Clients pick their entry via rivet/distribution's
platform + architecture filter, so every entry must be present and
correctly named.

## What the release pipeline enforces

- `scripts/check-release-version.sh`: VERSION == rivet.rktd == updater
  version == tag, before anything builds.
- CHANGELOG must have a section for the version (release notes are cut
  from it).
- The signed manifest step hard-fails the publish when the key secret
  is missing or signing produces no manifest.
